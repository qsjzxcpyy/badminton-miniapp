# 羽毛球双打微信小程序 · 设计文档

日期：2026-09-20
状态：已确认（设计阶段）

## 1. 背景与目标

球馆每周约一次羽毛球双打活动，6~8 人、单场地、总时长约 3 小时。需要一个手机小程序：
管理员创建比赛并管理球员名单与水平等级；球员点开即可查看赛程、记录每小局比分；
系统按净胜分实时排名。

目标用户：年轻业余球员，偏好绚丽、互动性强的界面。

## 2. 已确认的边界决策

| # | 决策点 | 结论 |
|---|---|---|
| 1 | 运行形态 | uni-app (Vue2) 编译为微信小程序；后端 FastAPI 部署到微信云托管（球馆内大家用手机流量，后端必须公网可访问） |
| 2 | 人数规模 | 按 6~8 人优化，算法支持任意人数 |
| 3 | 身份机制 | 邀请口令进入 + 名单认领（无微信登录）；管理员密码区分管理权限 |
| 4 | 计分规则 | 固定 15 分制：先到 15 即胜，无加分；胜方比分必须为 15 |
| 5 | 排班算法 | 约束过滤 + 评分搜索（方案 1）+ 周期性洗牌局（方案 A） |
| 6 | 部署 | 微信云托管（免域名免备案，自带 HTTPS），SQLite 存储 |
| 7 | 等级可见性 | 高/中/低仅管理员可见；普通球员视角无任何等级字样 |

## 3. 系统架构

```
微信小程序 (uni-app + Vue2)
        │  HTTPS REST API（wx.request 封装）
        ▼
FastAPI 后端 ── Docker 镜像 ── 微信云托管
        │
     SQLite（比赛数据量极小，零运维）
```

- 前端：uni-app Vue2 语法，编译目标微信小程序；开发期用微信开发者工具调试。
- 后端：FastAPI + SQLite，Docker 化部署微信云托管。
- 无用户系统：邀请口令 + 名单认领识别球员；认领票据（随机设备 ID）存手机本地。

## 4. 页面结构（6 页面 + 1 弹层）

| 页面 | 内容 |
|---|---|
| ① 进入页 | 输入 6 位邀请口令进入比赛；已认领则直接进主页 |
| ② 认领页 | 网格名单，点自己名字认领；已被认领者置灰 |
| ③ 比赛主页 | 当前第 N 局、场上 4 人卡片（"我"高亮）；比分记分牌（大数字）；我下一场第几局、还需休息几局 |
| ④ 赛程页 | 完整轮转表：每局 4 人分侧对阵、状态（未开/进行/完场比分）；混编局标 ⚡；已完成局可点开改比分 |
| ⑤ 排行榜 | 净胜分实时排名；每行：名次/名字/净胜分/胜局/总局数；前三名特殊样式 |
| ⑥ 管理页 | 密码进入：创建比赛（名称/时长/口令）、添加球员（姓名+等级）、生成赛程、重排剩余场次、移除球员 |

记分弹层：大号加减按钮（+1/+5）或直接输入；胜方锁定 15；二次确认后提交。

## 5. 数据模型（4 张表）

- **match**：id、名称、邀请口令（6 位）、管理员密码（hash）、总时长（分钟，默认 180）、状态
- **player**：id、match_id、姓名、等级（高/中/低）、认领票据（可空，认领后写入）
- **round**：id、match_id、序号、4 个球员 ID 及分侧、比分、状态（待打/完场）、版本号（乐观锁）、是否混编局
- **score_log**：id、round_id、旧比分、新比分、操作人、时间

排名不落库，实时计算：
净胜分 = Σ(己方得分 − 对方得分)；
并列时依次比较：净胜局 → 总局数少者优先 → 仍并列则同名次。

## 6. 排班算法 v2（洗牌增强版）

### 6.1 硬约束（任何一局含洗牌局，违反即组合非法）

1. **等级跨度 ≤ 1 级**：高不与低同局。
2. **等级组合规则**：
   - 2 高 2 中 → 高各带一中（HM vs HM）
   - 3 高 1 中 → 两高 + 一高中（HH vs HM）
   - 1 高 3 中 → 禁止
   - 中/低完全同理（2M2L → ML vs ML；3M1L → MM vs ML；1M3L → 禁止）
   - 4 人同级 → 自由配对
3. **局数均衡硬性容差**：生成过程中任意两人"已上场局数"差 ≤ 1。8 人 15 局 → 每人 7 或 8 局；6 人 15 局 → 每人 10 局；7 人 → 每人 8~9 局。
4. **连打限制（按人数自适应）**：普通局最少连打人数 = max(0, 4 − (N − 4))：8 人时 0 人连打（上局休息的 4 人全上）；7 人时 1 人连打；6 人时 2 人连打。任何情况下同一人不得连续上场超过 2 局。

### 6.2 洗牌局机制

- 仅当人数 ≥ 8 时启用（6/7 人时每局本就自然混编，无需洗牌）。
- 每 3 局一次（第 3、6、9、12、15 局）。
- 从刚打完的 4 人中抽 1~2 人留下连打，从休息的 4 人中补足，组成新 4 人。
- 抽人先过等级硬约束校验；不合法（如凑出 1 高 3 中）则换抽法重试；极端等级分布下找不到合法混编时降级为普通局，洗牌标记顺延。
- 刚连打的人后续强制优先休息，由容差约束自然补偿，最终局数仍人人一致。

### 6.3 软评分（合法组合中择优）

休息间隔方差 ↓ + 搭档新鲜度（历史搭档次数少优先）+ 对手新鲜度。

### 6.4 生成流程

1. 总局数 N = floor(总时长 / 每局估时)，每局估时 12 分钟（15 分制约 10~15 分钟），180 分钟 → 15 局。
2. 逐局生成：枚举当前合法 4 人组合（普通局从上局未上场者取；洗牌局按 6.2 取）→ 硬约束过滤 → 软评分排序 → 取最优。
3. 特殊情况：奇数人自动轮空处理；管理员移除球员 → 重排剩余未打场次（已完场比分与排名保留）。

### 6.5 效果承诺

- 每人上场局数差 ≤ 1（硬保证）。
- 8 人 15 局时每人至少与 4~6 个不同的人搭档、与几乎所有人对抗。
- 等级对抗始终满足 7.1/7.2 规则。

## 7. API 设计（9 个核心接口）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | /api/match | 创建比赛（名称/时长/口令/管理密码） |
| POST | /api/match/{id}/players | 添加球员（管理员） |
| POST | /api/match/{id}/schedule | 生成赛程（管理员） |
| POST | /api/match/{id}/claim | 球员认领（口令 + 名单选择） |
| POST | /api/round/{id}/score | 记分（版本号乐观锁 + score_log） |
| GET  | /api/match/{id}/ranking | 实时排名 |
| POST | /api/match/{id}/reschedule | 重排剩余场次（管理员） |
| POST | /api/match/{id}/remove-player | 移除球员（管理员） |
| POST | /api/match/{id}/state | 获取比赛全量数据（含当前局/赛程/排名） |

管理员鉴权：管理密码换取 token，管理操作请求头携带。

## 8. 错误处理

- 比分防误改：二次确认 + 校验（0~15，胜方必须 15，败方 0~14）。
- 并发记分：版本号乐观锁，冲突时提示刷新后重试。
- 认领冲突：一人只能被认领一次，重复认领返回明确错误。
- 口令错误：明确提示，不泄露比赛是否存在。
- 弱网：提交失败本地提示重试，不自动重复提交。

## 9. 视觉方向：「夜场球馆 · 荧光对决」

- **色彩**：深墨绿球场底 #0D1F1A；羽毛球荧光黄 #D8F34E（主强调）；球场线白 #F2F7F0；珊瑚红 #FF5A5F（客队/警示）；青柠 #7BE0AD（主队/成功）。
- **签名元素**：球场线语言——卡片、排行榜、记分牌用羽毛球场地线（边线/发球线/中线）做描边与分隔。
- **字体**：数字/比分用运动感精简数字字体包；中文用系统字体。
- **动效**：记分后排名条目位移交换、当前场次卡片呼吸光晕、认领成功羽球击出动效；动效克制，仅在得分/排名变化时出现。
- **等级显示**：管理员视角显示为球拍图标数量（🏸×3=高）；普通球员视角完全隐藏。
